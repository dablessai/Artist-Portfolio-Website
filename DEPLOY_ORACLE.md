# Deploying the ported site on Oracle Cloud

Target (updated 2026-10-27, second E2): the instance that actually exists is `artbymukherjee-e2` — Oracle Linux 9, VM.Standard.E2.1.Micro, Always Free-eligible, Hyderabad AD-1 FD-2, public IPv4 **140.245.226.75** (ephemeral — do not stop the instance, or the IP may change and BigRock DNS would need updating). The first E2 (140.245.211.5) was terminated on 2026-10-27 after its SSH key was lost; its IP is dead. Inbound 22 / 80 / 443 are already open. Nothing here creates an instance, changes a region, or upgrades the account; the planned A1 name `artbymukherjee-vm` remains available for a later A1 attempt and does not affect this E2.

SSH access (2026-10-27): the new E2's private key file is in Muse's browser downloads (filename only is recorded in MEMORY.md; key contents are never recorded). Outbound SSH from Muse must be allowed in Muse settings (Permissions → Direct network protocols → ssh on Ask) or scp/ssh will be refused by the VM proxy.

Before you start, on DNS at BigRock (where artbymukherjee.in lives): an A record for artbymukherjee.in to 140.245.226.75, and www to the same IP — but only after the site is deployed and tested by IP. DNS can take minutes to hours to propagate.

Steps: install Bun via its official installer, copy this folder to the server with scp, run bun install, then bun run build.
First run: PORT=3000 bun run start. First start creates data/artbymukherjee.db and seeds it.
Log in to Admin with the current admin login email and password set on 2026-10-27 (NOT the original seeded credentials — those no longer work), and fill in real contact details, bio and commission prices. Admin login rate limiting is now in place (5 failed attempts = 15-minute lockout, ported-site counters are in-memory and clear on restart).

Razorpay (test mode, built 2026-10-27): checkout is wired to Razorpay, but keys are NOT in this folder, in Admin Settings, or in chat. On the server, set the environment variables RAZORPAY_KEY_ID and RAZORPAY_KEY_SECRET (test keys for now) in the systemd service Environment= lines, then restart the service. Without them, checkout tells the buyer payment is not configured and creates no order. When the site goes live and Razorpay verifies it, replace those two variables with the live keys and restart — no code change, and never paste a Secret into Admin Settings.

Shop safety note (updated 2026-10-27): the old critical unpaid-order flaw is now FIXED for Razorpay checkout — the server re-prices every item from the database and marks an artwork Sold only after the Razorpay payment signature verifies. The old placeOrder action now rejects outright. A deploy without Razorpay keys cannot sell anything, which is the safe failure mode; a deploy with test keys sells only in Razorpay test mode (no real money).

Resend order emails (built 2026-10-27, code only — NOT yet live): after a verified payment creates an order, the server sends an order-confirmation email to the buyer and a new-order alert to the artist (recipient: the site's contact email setting, default artbymukherjee@gmail.com); Admin order updates that change status/courier/tracking also email the buyer. Email is best-effort: if the key is unset, sending is skipped (logged) and orders still complete; a failed send never fails an order. To activate: (1) create a Resend account and verify the sending domain in Resend (add its DNS records at the domain's DNS host) — until the domain is verified, Resend will not deliver from it; (2) set RESEND_API_KEY and optionally RESEND_FROM (default orders@artbymukherjee.in) in the server environment (same systemd EnvironmentFile / Environment= lines as the Razorpay keys — never in code, seed, chat, or Admin Settings); (3) restart the service; (4) place a real test order and check the buyer's inbox and the artist's inbox (including spam). Without the key, the confirmation page's email wording still over-promises — either activate email or correct that wording before launch.
Email logo: the brand logo lives in code at client/public/logo.png (copied from the user-uploaded logo file; white-on-black artwork), and the small email copy at client/public/logo-email.png (360px, made for emails). Vite copies both into client/dist/ on every build, so they ship with the normal code upload + rebuild — never put them in data/. Order emails reference the small copy as the hosted image https://artbymukherjee.in/logo-email.png (alt "ArtByMukherjee") inside a dark header band; do not switch it to a base64 data URI.
Run as a systemd service for auto-start on reboot (see README for the unit file pattern: WorkingDirectory is the project folder, ExecStart runs bun on server/src/index.ts, PORT=3000, Restart=always).
HTTPS: put nginx in front as a reverse proxy to port 3000, pass Host and Cookie headers through, and use certbot for Lets Encrypt certificates for artbymukherjee.in and www.
Backups: copy data/artbymukherjee.db daily and keep 7 days; also download a copy before any upgrade. Admin-uploaded photos live in data/uploads/ — back that folder up with the DB, since artwork rows point at /uploads/... files.
Updating: back up the DB, copy in new code without overwriting data/, bun install, bun run build, restart the service.

Not yet done in this port: live Razorpay keys (test mode only until Razorpay verifies the live site) and real Google/X login for comments (simulated as in the original). Admin photo upload IS built (2026-10-27, code only — not yet deployed): Admin → Artworks → "Upload new photo" (JPEG/PNG/WebP, max 5 MB), stored in data/uploads/ and served at /uploads/...; deploying it means uploading this code and restarting the service, without overwriting data/.
